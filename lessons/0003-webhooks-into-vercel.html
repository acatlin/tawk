Webhooks into Vercel: verify, dedupe, store

The only channel from tawk.to to your server: four events, one signature, a retry policy that will double-deliver, and a transcript stream that teaches your FAQ.

Time 30 minutes Builds on Lesson 1 Win A Vercel endpoint that rejects forgeries, ignores retries, and stores transcripts
By the end you can
  • Name the four webhook events, their key fields, and the one thing none of them gives you.
  • Verify the HMAC-SHA1 signature over the raw body in a Vercel function, in constant time.
  • Make the endpoint idempotent with X-Hook-Event-Id and fast enough for the 30-second timeout.
  • Turn transcripts into FAQ variants and a handoff log.

Why this matters for your bot

In Pattern A your bot already knows its own conversations. What it does not know is what happened after the handoff: whether a human picked up, what they said, what the visitor really wanted. Webhooks are how tawk.to tells you. They close the loop that lesson 4 depends on (real questions become FAQ variants) and give you the handoff analytics that lesson 6 reports on.

The four events

tawk.to posts JSON to your URL for exactly four events; nothing fires per message, so the conversation is never streamed to you live.tawk.to webhooks reference

EventFires whenFields you will use
chat:start“the first message in a chat is sent by visitor or agent. Whispers and system notifications like triggers do not generate this event.”chatId, time, domain, message.text, message.sender.type, visitor.{name,email,city,country}, property.id

A transcript of the entire conversation is sent after 3 minutes of inactivity.”tawk.to Help: creating and managing webhookschat.id, chat.visitor, chat.messages[] with sender.t (a agent, v visitor, s system), msg, time, optional attchs[]

Two consequences. First, the payloads carry the visitor’s name and email but not the custom attributes or tags you set in lesson 2, so if you want to join a tawk.to transcript to a bot session, put a short session reference in the drafted summary message; it will be in the transcript. Second, “the first message” means chat:start arrives with a message.text: in a handoff that is your drafted summary.

The signature

“Each webhook event is signed via a Hash-based Message Authentication Code (HMAC) using the webhooks secret key. The HMAC-SHA1 algorithm is used to generate the webhook payload signature. The signature is passed along with each request in the headers as ‘X-Tawk-Signature.’”tawk.to webhooks reference The official Node example computes a hex digest over the raw request body; it even configures body-parser’s verify hook just to capture those bytes before parsing.

The byte rule

An HMAC is over bytes, not over meaning. If you JSON.parse the body and sign JSON.stringify of the result, whitespace and key order can differ and the signature will not match. Capture the raw body first, verify, and only then parse. In a Vercel function with the web-standard handler signature that is one line: const rawBody = await request.text(). Vercel verifies its own webhooks the same way.Vercel docs: webhooks API (signature validation)

Compare in constant time. Node’s crypto.timingSafeEqual needs equal-length buffers, so check length first; the tested module does this for you:

export function signTawkPayload(rawBody: string | Buffer, secret: string): string {
  return createHmac("sha1", secret).update(rawBody).digest("hex");
}

export function verifyTawkSignature(rawBody: string | Buffer, signature: string | null | undefined, secret: string): boolean {
  if (!signature) return false;
  const expected = Buffer.from(signTawkPayload(rawBody, secret), "hex");
  let given: Buffer;
  try { given = Buffer.from(signature.trim(), "hex"); } catch { return false; }
  if (given.length !== expected.length || given.length === 0) return false;
  return timingSafeEqual(given, expected);
}

Retries: design for duplicates

“A webhook call will be retried for up to 12 hours if the http endpoint responds with anything but a success (2XX). If no response is received within 30 seconds, the call will be considered a failure and will also be reattempted. Each webhook event is assigned an event Id. The event Id is passed along with each request in the headers as X-Hook-Event-Id. The event Id will remain the same in case of retries.”tawk.to webhooks reference The help centre adds the operational translation: “Make sure your system can handle duplicate requests safely.”tawk.to Help: sending chat transcripts via webhooks

  • Idempotency key: store processed X-Hook-Event-Id values in a shared store (Postgres, KV). A module-level Map lives in one function instance and vanishes between invocations; it is fine for tests, wrong for production.
  • Respond first, work later: verify, dedupe, persist the raw event, return 200. Summaries, FAQ mining and notifications run afterwards, from a queue or via waitUntil from @vercel/functions.Vercel docs: Functions API reference Thirty seconds is generous for a database insert and stingy for a model call.
  • Return 2XX for events you ignore, or tawk.to will keep retrying them for twelve hours.

The handler, in order

import { handleTawkWebhook, MemoryWebhookStore, TAWK_EVENT_ID_HEADER, TAWK_SIGNATURE_HEADER } from "../src/tawk-webhook.js";

const store = new MemoryWebhookStore();   // swap for Postgres/KV: memory is per-instance

export async function POST(request: Request): Promise<Response> {
  const rawBody = await request.text();                       // the exact bytes tawk.to signed
  const result = await handleTawkWebhook(
    { rawBody, signature: request.headers.get(TAWK_SIGNATURE_HEADER), eventId: request.headers.get(TAWK_EVENT_ID_HEADER) },
    { secret: process.env["TAWK_WEBHOOK_SECRET"] ?? "", store,
      onEvent: async (event) => { if (event.event === "chat:transcript_created") { /* enqueue for FAQ mining */ } } },
  );
  return new Response(result.body, { status: result.status });
}

Vercel Functions accept this web-standard POST(request: Request) export directly.Vercel docs: Functions API reference The handler itself (handleTawkWebhook) has no framework dependency, which is why its seven tests run without a server.

Configure it in tawk.to

  1. Deploy, so the URL exists: https://your-app.vercel.app/api/tawk-webhook. “The URL must support HTTPS and accept JSON POST requests.”tawk.to Help: sending chat transcripts via webhooks
  2. In tawk.to: Administration → Settings → Webhooks → Create Webhook; give it a name, the endpoint URL, and tick the events. “You can have up to 10 webhooks per property.”tawk.to Help: creating and managing webhooks
  3. Put the webhook’s secret key into Vercel as TAWK_WEBHOOK_SECRET for the environment that serves that URL. The developer page says every webhook “consists of … A secret key”; the dashboard shows it on the webhook you created. If you register a second webhook for a staging URL, it gets its own secret.
  4. Send yourself a signed test from your machine, twice with the same id, then once tampered: 
    cd examples
npx tsx scripts/send-test-webhook.ts https://your-app.vercel.app/api/tawk-webhook "$TAWK_WEBHOOK_SECRET" chat:start --id test-1
npx tsx scripts/send-test-webhook.ts https://your-app.vercel.app/api/tawk-webhook "$TAWK_WEBHOOK_SECRET" chat:start --id test-1
npx tsx scripts/send-test-webhook.ts https://your-app.vercel.app/api/tawk-webhook "$TAWK_WEBHOOK_SECRET" chat:start --tamper
    Expect 200 ok chat:start, then 200 duplicate ignored (once your store is shared), then 401 invalid signature.

What to do with transcripts

A transcript is a list of messages with sender type a, v or s. The module’s transcriptToText() flattens one into “role: text” lines. Two jobs run on them weekly:

  • FAQ mining (lesson 4): every visitor line in a chat that reached a human is a candidate variant or a candidate new entry. Group by your FAQ ids using the matcher itself, and read the fall-throughs.
  • Handoff log (lesson 6): join the transcript to the bot session via the reference you put in the drafted summary, and compute handoff rate, time to first agent message, and the reasons that led there.
