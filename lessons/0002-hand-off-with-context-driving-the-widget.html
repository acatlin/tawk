Lesson 2 of 8 · The human channel

Hand off with context: driving the widget

In Pattern A your bot talks first. When it hands off, the human agent should already know who this is, what was tried, and why. The JavaScript API gives you exactly the levers to make that true.

Time 30 minutes Builds on Lesson 1 Win An escalateToHuman() that identifies the visitor, attaches context, drafts a summary and opens the chat, verified against a simulator
By the end you can
  • Embed the widget correctly and call the API only when it is ready.
  • Identify the visitor with secure mode, with the hash computed on your Vercel server.
  • Attach attributes, tags and events within tawk.to’s documented limits, and draft the handoff summary.
  • Use callbacks to coordinate your bot’s UI with the widget’s lifecycle.

Why this matters for your bot

A handoff is a seam between two surfaces, and seams are where visitors repeat themselves and churn. The only thing that makes the seam invisible is context transfer: identity (so the agent sees the account and the previous conversations), structured facts (what tier answered, what failed), and a human-readable summary as the first message. tawk.to exposes one documented lever for each.

Embed, then wait

The widget script URL is https://embed.tawk.to/{propertyId}/{widgetId}; the default widget’s ID is default. tawk.to’s own Android sample and its React wrapper build exactly that URL.tawk.to official Android sample (Bitbucket)tawk-messenger-react (GitHub)

<script>
  var Tawk_API = Tawk_API || {}, Tawk_LoadStart = new Date();
  // Settings that must exist BEFORE the script loads:
  Tawk_API.autoStart = false;                 // connect only when you need it (privacy, performance)
  Tawk_API.customStyle = { zIndex: 1000 };    // officially: zIndex only
  (function () {
    var s1 = document.createElement('script'), s0 = document.getElementsByTagName('script')[0];
    s1.async = true;
    s1.src = 'https://embed.tawk.to/' + PROPERTY_ID + '/' + WIDGET_ID;
    s1.charset = 'UTF-8';
    s1.setAttribute('crossorigin', '*');
    s0.parentNode.insertBefore(s1, s0);
  })();
</script>

Three things are read at load time and are ignored if set later: visitor, customStyle, and autoStart. Everything else is a method you call after the widget is ready; the reference wraps every example in onLoad, and the help centre calls calling methods too early “one of the most common mistakes.”tawk.to JavaScript API referencetawk.to Help: behind the scenes of the JavaScript API autoStart With autoStart = false the widget stays hidden and disconnected until you call Tawk_API.start({ showWidget: true }). For a bot-first UI that is the right default: the human channel appears when the bot decides it is needed.

Identify the visitor: secure mode

Unidentified visitors are fine for anonymous help. For anyone signed into your product, identify them so the agent sees their history and so attributes stick to a person. tawk.to accepts a name and email only when accompanied by a hash: “The hash is server side generated HMAC using SHA256, the user’s email and your site’s API key.”tawk.to JavaScript API reference The key lives at Administration → Overview → JavaScript API, where you enable Secure Mode and copy it.tawk.to Help: generating a hash for the JavaScript API It never ships to the browser.

Three documented ways to pass identity, pick by when you know who the user is:tawk.to developer portal: set name and email

  1. Known before the page loads: set Tawk_API.visitor = { name, email, hash } before the script.
  2. Known later (single-page app, AJAX login): inside onLoad, call Tawk_API.setAttributes({ name, email, hash }, cb).
  3. You want previous conversations restored (same person, web and Android): Tawk_API.login({ userId, hash, name, email }, cb), where the hash is “a combination of userId + site API key using HMAC SHA256”; it “will retrieved the conversation of the user if it has existing before.”tawk.to JavaScript API reference
A documented ambiguity

The reference page hashes the email for visitor/setAttributes and the userId for login; three help-centre articles say “user ID” for both. The login case is unambiguous. For setAttributes, follow the reference page’s PHP example (email), test once against your dashboard, and keep the identifier in one place in code so switching is a one-line change. A wrong hash does not throw loudly: “If the hash is missing or doesn’t match, the widget will not update the visitor’s details.”tawk.to Help: pre-chat name and email with the JavaScript API login reports a 401 in the console when the hash and userId disagree.tawk.to Help: logins with a hash

The server side is tiny. From the tested module:

import { createHmac } from "node:crypto";

/** HMAC-SHA256 (hex) of an identifier (email for `visitor`, userId for `login`) with the site API key. */
export function visitorHash(identifier: string, siteApiKey: string): string {
  return createHmac("sha256", siteApiKey).update(identifier, "utf8").digest("hex");
}
import { visitorHash } from "../src/tawk-secure-mode.js";

export async function GET(request: Request): Promise<Response> {
  const user = await requireSession(request);           // your auth: never trust a userId from the query string
  if (!user) return new Response("unauthenticated", { status: 401 });
  const key = process.env.TAWK_SITE_API_KEY!;
  return Response.json({
    userId: user.id,
    hash: visitorHash(user.id, key),                      // for Tawk_API.login
    emailHash: visitorHash(user.email, key),              // for visitor / setAttributes
    name: user.name, email: user.email,
  });
}

Limits and error codes from the reference.tawk.to JavaScript API reference Every setter takes a callback that receives an error string or nothing; log it, because these calls fail silently otherwise.

Why draft rather than send? Because tawk.to has no send. The draft is the honest version of “bot posts a summary”: the visitor reads it, edits it if the bot got something wrong, and presses Send, so the first message the agent sees is a vetted summary rather than a blank “hi”.

Coordinate the two surfaces

Callbacks are how your UI follows the widget. The ones that matter for handoff:

  • onChatStarted: hide your bot composer; the human channel owns the conversation now.
  • onAgentJoinChat({ name, position, image, id }): show “Dana joined” in your UI; stop any bot timers.
  • onChatMessageAgent(message): since widget 0.2.0 the payload is an object, { message?: string, attachments: [...] }, not a string.tawk.to developer product updates
  • onChatEnded: bring the bot back, optionally ask for a rating.
  • onStatusChange(status) and getStatus(): when agents are offline, offer a ticket or email instead of an empty chat.

Most callbacks are “not supported in pop out chat window,” so avoid popup() for bot-coordinated flows.tawk.to JavaScript API reference

The panel below is a simulator of the widget and its API (same names, limits and error codes). SimServer.hashFor(id) stands in for your Vercel identity route. Complete the TODOs, click Run, then use the simulator’s buttons to play the agent. The grader checks the five things a good handoff does.

Your escalateToHuman()

async function escalateToHuman(summary, reason) {
  const api = window.Tawk_API;
  const userId = 'user-42';

  // 1. Identity: the hash comes from your server, never computed in the browser.
  const hash = await SimServer.hashFor(userId);
  await new Promise((done) => api.login({ userId, hash, name: 'Andy', email: 'andy@example.com' },
    (err) => { if (err) console.warn('login failed:', err); done(); }));

  // 2. Context agents can filter and read.
  api.setAttributes({ 'bot-last-reason': reason, 'bot-last-tier': 'fallback' }, (err) => err && console.warn(err));
  api.addTags(['bot-handoff'], (err) => err && console.warn(err));
  api.addEvent('bot-handoff', { reason }, (err) => err && console.warn(err));

  // 3. Draft the summary; the visitor presses Send.
  api.setChatInputMessage(summary, (err) => err && console.warn(err));

  // 4. Open the human channel.
  api.maximize();
}

window.Tawk_API.onAgentJoinChat = (agent) => console.log('human joined:', agent.name);
window.Tawk_API.onChatEnded = () => console.log('chat ended: resume the bot UI');

Carry it into your project

  • Secure Mode enabled; TAWK_SITE_API_KEY in Vercel (dev and prod); never in client code.
  • An authenticated identity route returns { userId, hash } for the signed-in user.
  • escalateToHuman() sets attributes, tags, an event, drafts a summary, and opens the widget; all callbacks log errors.
  • Your UI reacts to onChatStarted, onAgentJoinChat, onChatEnded, onStatusChange.
  • When status is offline, the bot offers a ticket or email instead of an empty chat.
