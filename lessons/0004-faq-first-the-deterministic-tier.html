FAQ-first: the deterministic tier

The cheapest, fastest, most auditable tier answers first. Its one job is to never be confidently wrong.

Time 25 minutes Builds on Lesson 1 (your integration pattern) Win A FAQ matcher with a threshold you tuned against a test set

Why this matters for your bot

You asked for answers to “come first from a provided FAQ if available.” That instinct is shared by every bot platform that has run at scale. A FAQ hit is deterministic (the same question always gets the same curated wording), cheap (no tokens), fast (microseconds), and auditable (you can print every answer the tier will ever give). A model answer is none of those things, however good it is. So the model should see only the questions the FAQ cannot answer.

Rasa calls this a retrieval intent with a rule: FAQs are “non-contextual questions” the assistant “should always answer the same way, no matter what has happened previously in the conversation,” and rules are training data “where a specific condition always predicts a specific next action.”Rasa Open Source docs: Chitchat and FAQs Google’s Dialogflow CX puts the generative model last by construction: its generative fallback runs only “when end-user input doesn’t match an intent,” and an FAQ data store returns the stored answer unchanged when a question is matched with high confidence.Dialogflow CX docs: Generative fallbackDialogflow CX docs: Data stores You are building the same ordering with fifty lines of TypeScript.

The FAQ entry

An entry is not a question and an answer. It is a cluster of phrasings, one canonical answer, and a pointer to where the answer lives in your approved sources (lesson 5), so the FAQ tier can cite just like the model tier does.

import type { FaqEntry } from "./faq-match.js";

export const FAQ: FaqEntry[] = [
  {
    id: "lost-card",
    questions: [
      "I lost my membership card",          // canonical phrasing first
      "My card is missing",                  // then paraphrases visitors actually type
      "How do I replace a lost card?",
    ],
    answer: "Report it in the app under Membership → Card. A replacement costs $10 and ships in 3–5 days.",
    source: "https://help.harbor.example/membership/card",   // inside your approved sources
  },
];
  • Variants come from transcripts, not imagination. Lesson 3’s webhook stores every chat transcript; once a week, read the questions that fell through and promote the recurring ones into variants. Synonym lists from a thesaurus rarely match how people type under stress.
  • Keep answers short and complete. The FAQ answer is served verbatim; a visitor should not need a follow-up to act on it.
  • One idea per entry. If “refunds” and “cancellation” share phrasings, the matcher will call them ambiguous (correctly). Split by the action the visitor wants, not by the page the answer sits on.
  • Date it. Add a reviewed field in your own schema and let a cron job flag entries older than a quarter. Stale FAQ answers are confidently wrong answers with a timestamp.

Matching: three strategies, one scale

Every strategy in the course module returns a score between 0 and 1, so a single threshold works whichever you choose. All three first normalise the text: lowercase, strip punctuation and apostrophes, drop stop words (“the”, “my”, “how”), and apply a tiny stemmer so bikes and bike agree.

StrategyWhat it comparesUse when
exactNormalised question equals a variantButtons and canned chips, where you control the text
jaccardToken-set overlap with the best variantShort questions, tiny FAQs; easy to explain to a colleague
tfidf (default)Cosine similarity of tf-idf vectors over variants and the answerMost FAQs; rare words like “refund” count for more than “card”

When your FAQ grows past a few hundred entries or visitors write long messages, step up in this order: a proper BM25 engine such as MiniSearch (BM25+, fuzzy and prefix matching, zero dependencies, runs in Node and the browser),MiniSearch repository then embeddings. Anthropic does not offer an embedding model and recommends Voyage AI’s, with an official TypeScript client.Claude docs: Embeddings For a curated FAQ, though, good variants plus lexical matching usually beat embeddings on precision, and precision is what this tier is for.

The two dials

Dial 1 · threshold

Minimum top score

Below it, the FAQ stays silent and the question falls through to retrieval. Raising it trades missed hits for fewer wrong ones.

Dial 2 · ambiguity margin

Gap to the runner-up

If the top two entries score within the margin, the FAQ declines even when the top clears the threshold. This catches sibling entries (“change email” vs “change email password”) that a single threshold cannot.

Here is the whole decision, from the tested module:

export function matchFaq(faq: FaqEntry[], question: string, opts: FaqMatchOptions = {}): FaqDecision {
  const { strategy = "tfidf", threshold = 0.5, margin = 0.1 } = opts;
  const ranked = rankFaq(faq, question, strategy);
  const top = ranked[0], second = ranked[1];
  if (!top || top.score <= 0)                         return { hit: false, reason: "empty", ranked };
  if (top.score < threshold)                           return { hit: false, reason: "below-threshold", ranked };
  if (second && margin > 0 && top.score - second.score < margin)
                                                       return { hit: false, reason: "ambiguous", ranked };
  return { hit: true, entry: top.entry, score: top.score, ranked };
}
Wrong beats missed, and not in a good way

A missed FAQ hit falls through to the retrieval tier, which can still answer with citations or hand off to a person. A wrong FAQ hit serves a confident, verbatim answer to the wrong question, and the visitor has no way to tell. Tune for zero wrong first; only then lower the threshold to recover misses. Measure both with a test set, every time the FAQ changes.

Do it: tune the dials

The lab below runs the same normalisation and scoring as examples/src/faq-match.ts. The test set mixes paraphrases, near-collisions and out-of-scope questions (expected answer null).

  1. Type a few questions and read the ranked scores. Notice how the answer text helps (“how much is a replacement card” finds the entry whose answer mentions a replacement).
  2. Run the test set at the default threshold. Count wrong and missed.
  3. Set the ambiguity margin to 0 and lower the threshold in small steps until the first wrong answer appears (around 0.2 on this FAQ: an out-of-scope question lands on the e-bike entry). Now restore the margin to 0.1 and run again: the margin rescues that case because the runner-up was close. The clean-sweep window is where your real threshold should sit, with a little headroom.
  4. Open the FAQ JSON, add one variant that rescues a missed question, apply, re-run. This is the weekly loop you will run on real transcripts.
  5. Switch strategies and repeat. Jaccard and tf-idf will want different thresholds; that is why the number lives in config, not in code.

Where it runs

Inside the same Vercel function that calls the model, before the call. The FAQ can ship as a JSON file in the repo (every deploy is a review), or live in a table your team edits. The pipeline in lesson 6 makes this tier 1:

const faq = matchFaq(deps.faq, question, deps.faqOptions);
if (faq.hit) {
  return { tier: "faq", text: faq.entry.answer, citations: [{ title: "FAQ", url: faq.entry.source }], confidence: faq.score, handoff: false, reason: `faq:${faq.entry.id}` };
}
// …otherwise fall through to approved-source retrieval

Carry it into your project

  • FAQ entries have id, 3+ variants, a short canonical answer, a source URL inside the approved sources, and a review date.
  • A test set with expected ids, including out-of-scope questions marked null, checked into the repo.
  • Threshold and margin live in config; the clean-sweep window is documented next to them.
  • A weekly reminder to mine fall-through transcripts for new variants.
  • npm test in examples/ is green after you edit the matcher.
