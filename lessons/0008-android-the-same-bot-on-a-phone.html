Android: the same bot on a phone

No SDK, no problem. Your bot’s UI is yours, the human channel is a WebView away, and the backend you built in lessons 3 to 6 does not change at all.

Time 30 minutes Builds on Lessons 2 and 6 Win A shell decision plus the WebView chat screen that identifies the visitor and receives the handoff
By the end you can
  • Choose between a Trusted Web Activity, Capacitor, and a native Kotlin app for your JavaScript stack.
  • Load the tawk.to widget in a WebView the way tawk.to’s own sample does, with the permissions it needs.
  • Carry one visitor identity across web and Android with login().
  • Deliver the handoff summary and bridge widget callbacks back to native code.

Why this matters for your bot

“It should also run on an Android app” sounds like a port. It is mostly a packaging decision, because everything that matters (the pipeline, the guards, the webhooks) already lives behind your Vercel API, and tawk.to’s chat is a web page. What is new on a phone is the shell, permissions for file uploads, the app lifecycle, and making sure the person is the same person they were on the web.

What tawk.to offers on Android

There is no SDK: “A Mobile SDK is in our development roadmap and we hope to release it soon. However, using the Direct Chat Link, you can still give customers the ability to connect with you in a mobile app.” The article recommends a WebView and reminds you to “Make sure JavaScript is enabled in any WebView or in-app browser.”tawk.to Help: adding the widget to your mobile application tawk.to staff point developers to an official Kotlin sample that wraps the widget in a WebView; it is a sample app you copy from, not a library you depend on (two commits, September 2023; minSdk 24, compileSdk 33).tawk.to official Android sample (Bitbucket) An iOS sibling using WKWebView appeared in December 2025.tawk.to official iOS sample (Bitbucket)

The WebView chat screen, from tawk.to’s sample

tawk.to’s Kotlin sample loads an HTML template that contains the normal embed snippet, enables the WebView features the widget needs, and bridges two callbacks back to Kotlin.tawk.to official Android sample (Bitbucket) The essential lines:

val webSettings = webView.settings
webSettings.javaScriptEnabled = true
webSettings.domStorageEnabled = true
webSettings.databaseEnabled = true
webSettings.allowFileAccess = true
webView.webViewClient = WebViewClient()
webView.webChromeClient = WidgetWebChromeClient(this)          // file chooser + permission prompts
webView.addJavascriptInterface(WidgetJavascriptInterface(this), "WidgetJavascriptInterface")

val widgetConfig = WidgetConfig(propertyId = "000000000000000000000001", widgetId = "default")
val htmlData = WidgetHtmlParser(application).parse(widgetConfig = widgetConfig, customVariables = customVariables)

// Base URL matters: the widget must think it is on the web, not on file://
webView.loadDataWithBaseURL("https://embed.tawk.to/", htmlData, "text/html", "UTF-8", null)

The iOS README makes the base-URL point explicit: “Using https://tawk.to as the base URL ensures the widget treats the environment as a valid web context (vs. file://).”tawk.to official iOS sample (Bitbucket) The sample’s manifest declares INTERNET, network state, storage/media and WAKE_LOCK, and requests CAMERA and media permissions at runtime so visitors can attach photos.

Here is the template adapted for your handoff: identity via login, the drafted summary, and callbacks bridged to native. Placeholders in ${…} are filled by your app before loading; the hash and summary come from your own API, never computed on the device.

<!doctype html><html><head><meta name="viewport" content="width=device-width, initial-scale=1"></head><body>
<script>
  var Tawk_API = Tawk_API || {}, Tawk_LoadStart = new Date();
  Tawk_API.onLoad = function () {
    // 1. Same identity as the web: userId + server-computed hash (lesson 2)
    Tawk_API.login({ userId: '${user.id}', hash: '${user.hash}', name: '${user.name}', email: '${user.email}' }, function (err) {
      if (err) WidgetJavascriptInterface.onError('login:' + err);
    });
    // 2. Context + the drafted summary from the bot (lesson 6)
    Tawk_API.setAttributes({ 'bot-last-reason': '${handoff.reason}', 'platform': 'android' }, function () {});
    Tawk_API.addTags(['bot-handoff', 'android'], function () {});
    Tawk_API.setChatInputMessage('${handoff.summary}', function () {});
    Tawk_API.maximize();
  };
  // 3. Bridge lifecycle back to Kotlin
  Tawk_API.onChatMinimized = function () { WidgetJavascriptInterface.onChatMinimized(); };
  Tawk_API.onChatEnded     = function () { WidgetJavascriptInterface.onChatEnded(); };
  Tawk_API.onAgentJoinChat = function (a) { WidgetJavascriptInterface.onAgentJoined(a.name); };
  Tawk_API.onStatusChange  = function (s) { WidgetJavascriptInterface.onStatus(s); };
  (function () {
    var s1 = document.createElement('script'), s0 = document.getElementsByTagName('script')[0];
    s1.async = true; s1.src = 'https://embed.tawk.to/${propertyId}/${widgetId}'; s1.charset = 'UTF-8'; s1.setAttribute('crossorigin', '*');
    s0.parentNode.insertBefore(s1, s0);
  })();
</script></body></html>

Escape the placeholder values for a JavaScript string (quotes, newlines) before substitution, exactly as you would for any template that becomes code. The sample’s WidgetHtmlParser does plain string replacement.

Identity across devices

login() is the device-independent identity: “This function will login a user using hash and userId. This will retrieved the conversation of the user if it has existing before.”tawk.to JavaScript API reference Your Android app calls the same identity route as the web (lesson 2), gets { userId, hash }, and injects them into the template. The site API key stays on the server. A visitor who started on the website and opens the app sees their previous conversation; the agent sees one person, not two.

Lifecycle, status, offline

  • Connection lifecycle. The iOS sample calls Tawk_API.shutdown() when the screen disappears and Tawk_API.start() when it reappears.tawk.to official iOS sample (Bitbucket) Mirror that in onPause/onResume with webView.evaluateJavascript(...), so a backgrounded app does not hold a live socket.
  • Status before opening the screen. If getStatus() (or the bridged onStatusChange) says offline, show your ticket/email path instead; the Direct Chat Link article warns “Ensure your chat widget is online; otherwise, customers cannot start a chat.”tawk.to Help: Direct Chat Link
  • The simplest fallback. If you want nothing custom at all, open the Direct Chat Link https://tawk.to/chat/{propertyId}/{widgetId} in an in-app browser. It cannot be pre-filled: staff confirmed in April 2026 that query parameters are not supported and the link “will always open a new, empty session.”tawk.to Community: Direct Chat Link parameters (staff reply) That is why the WebView template above exists.

Do it

  1. Choose the shell with the table. Write the choice under the architecture decision from lesson 1.
  2. Build the chat screen: copy the sample’s WidgetActivity, WidgetWebChromeClient and WidgetJavascriptInterface, replace widget.html with the template above, and add onChatEnded/onAgentJoined/onStatus/onError methods to the interface. (For Capacitor or a TWA, skip this: your web escalateToHuman() already does it.)
  3. Carry identity: call your identity route on app sign-in, store { userId, hash } in memory, pass them to the template.
  4. Wire the handoff: when answer() returns handoff: true, open the chat screen with reason and the drafted summary.
  5. Test on an emulator: online status shown; agent sees the logged-in name in the dashboard; the summary is pre-filled; attaching a photo prompts for permission; minimizing returns to your UI; backgrounding and returning reconnects.

Carry it into your project

  • App calls the identity route and logs the visitor in with login().
  • Handoff opens the chat screen with the drafted summary; callbacks bridged for minimize, end, agent joined, status.
  • shutdown()/start() on pause/resume; offline status routes to a ticket.
